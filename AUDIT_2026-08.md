## 1. Executive summary

The application is **materially healthier than the repo's existing audit documents claim**. `AUDIT_REPORT.md`, `QA_FULL_AUDIT.md` and `SCHEMA_FAILURE_REPORT.md` frame the system as being in critical failure. Runtime evidence does not support that: the app boots cleanly, the full test suite passes (87/87), and an authenticated crawl of all 254 GET routes returns **zero HTTP 500s** on both an empty and a populated database.

The real risk is concentrated somewhere else, and it is not visible from a crawl: **input validation on money and quantity fields is largely absent**. The framework-level defences (authn, authz, CSRF, SQL injection) are in good shape; the domain-level invariants that an ERP depends on are not enforced. I was able to dispatch 450 bags against a 100-bag booking, book a negative-value sale, and record a payment 100× larger than the invoice it settles — all through the normal UI endpoints, as a normal authenticated user, with no errors shown.

| Area | Verdict |
|---|---|
| Availability / stability | **Good** — 0 crashes across 254 routes, 87/87 tests pass |
| Authentication coverage | **Good** — every route except `/login` and `/api/ui/theme` requires auth |
| CSRF / SQLi / RCE | **Good** — no unprotected write path, no injectable SQL, no `eval`/`exec`/`pickle` |

## 2. Critical — business logic & data integrity

### 2.1 Negative dispatch defeats the over-dispatch guard (stock can be drained without limit)

**Severity: Critical.** This is the most serious finding in the audit.

`add_record` correctly refuses to dispatch more than a client has booked:

```python
# app/blueprints/ops/_dispatch_add_record.py:82
if req_qty > remaining:
    flash(f"Cannot dispatch {req_qty} bags. Only {remaining} bags available from booking. ...", 'danger')
    return redirect(url_for('dispatching'))
```

The check is one-sided. `req_qty` is parsed with a bare `float()` (line 55) and never tested for `> 0`. A negative quantity passes `req_qty > remaining` trivially, persists as an `Entry` with negative `qty`, and — because `remaining` is computed as `booked - dispatched` by summing those same entry rows — it **increases the remaining allowance**.

Reproduced end-to-end (`/tmp/aud/probe7.py`), against a booking of 100 bags:

```
booking items: [('CEMENT', 100.0)]
A over-dispatch:   qty=500  -> OUT rows=0  total=0     ['Cannot dispatch 500']   # guard works
B negative dispatch: qty=-400 -> OUT rows=1  total=-400.0  []                    # accepted silently
C exploit dispatch:  qty=450  -> OUT rows=2  total=50.0    []                    # accepted silently
FINAL: booked=100  dispatched_rows=[-400.0, 450.0]  net=50.0
```

Two requests convert a 100-bag entitlement into a 450-bag physical dispatch, while the ledger nets out to a plausible-looking 50. This is an inventory-theft primitive that any user with dispatch rights can operate, and the netting makes it hard to spot in summary views.

**Fix:** reject `req_qty <= 0` at parse time, and treat a `ValueError` in the `float()` conversion as a validation failure rather than silently coercing to `0`. Apply the same guard to every quantity field, not just this one. A database `CHECK (qty > 0)` constraint on `entry` is worth adding as a backstop.

### 2.2 No non-negativity or over-allocation invariants on money

Same class of defect, in `app/blueprints/sales/bookings.py`. `amount` and `paid_amount` go through `_to_float_or_zero` (lines 232–233, and again on edit at 375–376) with no range validation:

* **Negative booking accepted.** `qty[]=-100`, `amount=-100000` persists `Booking.amount = -100000.0`.
* **Overpayment accepted.** A booking with `amount = 10000.0` accepted `paid_amount = 999999.0`. There is no `paid <= amount` invariant.

The overpayment propagates into the books rather than being contained. Observed state after the probe:

```
BOOKINGS:  id=2 amount=10000.0  paid=999999.0
ACCOUNT:   CASH BOX balance=999999.30
CLIENTS:   PROBE CLIENT | billed 110,000.00 | paid 999,999.30 | -889,999.30 Advance
```

The client list renders an **889,999 "Advance"** — i.e. the system now believes the business owes this client nearly a million rupees, purely because of an unvalidated form field. `pending_amount = max(0.0, amount - discount - paid_amount)` (line 266) clamps the pending figure but does nothing about the underlying overpayment, so the error surfaces as a fictitious credit balance instead of a visible error.

**Fix:** validate `amount >= 0` and `0 <= paid_amount <= amount - discount` before constructing the `Booking`, on both the create and edit paths. Return a flash + redirect the way the discount parser already does.

### 2.3 Money is float-typed almost everywhere; drift is already present in stored data

`models/` contains **85 `db.Float` columns and zero `db.Numeric`/`DECIMAL`**:

```
models/cash.py:24   models/sales.py:31   models/stock.py:12   models/delivery.py:5
models/rentals.py:5 models/parties.py:4  models/catalog.py:2  models/core.py:1  models/ops_meta.py:1
```

There *is* a correct exact-decimal facility — `utils/money.py` (`to_minor`/`from_minor`, `ROUND_HALF_UP`) plus a `before_flush` hook in `models/events.py` that mirrors floats into integer `_minor` columns. But it only covers the cash/account/payment models. `Booking`, `PendingBill`, `DirectSale`, `Invoice`, `BookingItem` and the GRN/return lines are float-only.

This is not theoretical. Three payments of `0.10` each stored exact `amount_minor = [10, 10, 10]`, and the same probe left a receivable persisted as:

```
PENDING BILLS: id=1 amount=99999.69999999998
```

That value is now in the database and will be rendered, summed, and reconciled against. Anything that sums the float column instead of the minor column drifts.

**Fix (staged):** (a) make every *report* and *reconciliation* read the `_minor` column where one exists; (b) extend the `_minor` mirror to the sales models; (c) longer term, migrate the columns to integer minor units or `Numeric(18,2)`. Step (a) is cheap and stops the bleeding.

### 2.4 Concurrent writes are silently dropped

Twelve parallel `POST /add_payment` requests (`/tmp/aud/conc2.py`) produced:

```
8 × "Payment received successfully"
4 × "Unable to save payment: the payment could not be saved..."
PAYMENTS PERSISTED: 8 of 12    balance: 800.0
```

Credit where due: the failures **are** surfaced to the user and the account balance stayed exactly consistent (8 × 100 = 800), so this is not corruption. The underlying cause is `sqlalchemy.orm.exc.StaleDataError` on the `account` row — SQLite plus a read-modify-write on the balance means one third of concurrent submissions lose the race and are rolled back by the generic `except Exception` handler in `add_payment`.

For a single-branch deployment this is an annoyance. For anything with concurrent cashiers it is a reliability problem, and the generic error message gives the user no reason to believe a retry will work. Bill-number allocation, by contrast, is **correctly serialised** — `get_next_bill_no` takes the write lock first via `INSERT OR IGNORE` and produced **zero duplicate bill numbers** across the same 12-way concurrency test. That pattern is the right one; the balance update should adopt it (or use an atomic `UPDATE ... SET balance = balance + :delta` with a retry).

## 3. High — security

### 3.1 Plaintext password fallback in the login path

`models/core.py:57` declares a real `password_plain` column, and `app/blueprints/auth.py::_verify_and_upgrade_password` will authenticate against it — and also against a plaintext value sitting in the `password_hash` column:

```python
stored_plain = (getattr(u, 'password_plain', None) or '').strip()   # auth.py:53
```

On a successful plaintext match it upgrades the record to a proper hash and nulls the column (lines 64, 83), which is a reasonable migration strategy — but the accepting code path is still live, and the column still exists. A database leak therefore yields directly usable credentials for any account that has not yet logged in since the migration.

A remediation script exists (`tools/repair_controlled/clear_verified_plaintext_passwords.py`). **Run it, confirm `SELECT COUNT(*) FROM user WHERE password_plain IS NOT NULL` is zero, then delete the fallback branch and drop the column.** Leaving the fallback in place indefinitely means the migration never actually completes.

### 3.2 No rate limiting or account lockout anywhere

Greps for `rate_limit`, `lockout`, `failed_login` and equivalents return nothing across the entire codebase. `/login` accepts unlimited attempts. Combined with §3.1 this makes credential stuffing straightforward and cheap.

**Fix:** per-IP and per-username throttling on `/login`, plus a failed-attempt counter with temporary lockout. `flask-limiter` is a small dependency and would cover it.

### 3.3 Clickjacking and CORS are disabled globally

`app/hooks.py:81-92` sets, unconditionally, on **every** response:

```python
response.headers["X-Frame-Options"] = "ALLOWALL"
response.headers["Content-Security-Policy"] = "frame-ancestors *"
```

and with `ALLOW_OPEN_CORS=1`, `Access-Control-Allow-Origin: *`. Any site can frame the entire ERP and drive it via clickjacking against a logged-in session. Note this compounds with §3.4: session protection is off, so a framed session stays valid.

This looks deliberate (embedding the app in some parent portal). If so, replace the wildcards with an explicit `frame-ancestors <the-one-host>` allowlist rather than `*`.

### 3.4 Lower-severity security notes

* **CSRF is hand-rolled but sound** — `_protect_against_csrf` uses a session token and `compare_digest`, returns JSON 400 on API paths. However it is **fully disabled when `TESTING` or `WTF_CSRF_ENABLED is False`** unless `AMS_CSRF_ALWAYS` is set (`app/hooks.py:187-188`), which means the 87-test suite exercises essentially no CSRF path. Add at least one test with `AMS_CSRF_ALWAYS=1`.
* `login_manager.session_protection = None` — deliberate (the comment cites multi-IP logins), but it removes session-hijack detection.
* `wsgi.py` returns **raw startup tracebacks in 500 response bodies**. Gate on debug.
* **Hardcoded webhook token** `PakistanZindabad1947-2026` in `main.py:38`, guarding a `/git-auto-pull` endpoint that runs `git reset --hard` and redeploys. Anyone who reads this repo can force a deploy. Move to an env var with no default, and rotate.
* `GITHUB_REPO` and `wrangler.toml` point at a *different* project (`ams99`) — stale config on an auto-deploy path is dangerous. Reconcile or remove.

### 3.5 What is actually solid

Worth stating explicitly, because it narrows where remediation effort should go:

* **Authentication coverage is comprehensive.** An anonymous GET sweep of all routes found only `/login` (200) and `/api/ui/theme` (200) reachable; admin routes return 403; everything else redirects to login.
* **No unprotected write path.** An anonymous POST sweep *with a valid CSRF token* across every mutating endpoint found zero writes — the three non-redirect results were 400/405/404.
* **No SQL injection in any request path.** All raw f-string SQL operates on internal identifiers (`PRAGMA table_info`, `ALTER TABLE`, `COUNT(*)`) in `app/services/schema.py`, `health.py`, `app/__init__.py` and `tools/` scripts. No user input reaches it.
* **No `eval`, `exec`, `pickle.loads`, `os.system` or `shell=True`** in `app/`, `blueprints/`, `utils/` or `models/`.

## 4. Medium — schema, bootstrap, operations

### 4.1 The declared v4.4 schema file does not exist

`app/__init__.py` pins `AMS_SCHEMA_VERSION = v4.4` and resolves `AMS_V44_SCHEMA_PATH` to `<root>/v44/SCHEMA_v4_4.sql`. **There is no `v44/` directory in the repository.** Boot logs a fallback warning and proceeds, so the "official v4.4 schema" is never applied — the live database is whatever `db.create_all()` happens to produce from the ORM models.

Consequence: the constraints, indexes and `CHECK`s the schema file presumably declares are absent in production. This is very likely *why* §2.1 and §2.2 are exploitable — a `CHECK (qty > 0)` in that file would have stopped both. Either commit the schema file or delete the pinning machinery; the current half-state gives false assurance.

### 4.2 An ORM-bootstrapped database can never become "v4.4"

On restart the app logs `Existing non-v4.4 database ... left untouched`. Because the first boot creates the DB via `create_all()` rather than the (missing) schema file, it is permanently flagged non-v4.4 and no upgrade path will ever run against it. The guard is protecting a state the app can't reach.

### 4.3 Bootstrap errors are swallowed

Failures during factory bootstrap are captured into `AMS_BOOTSTRAP_ERROR` and the app **serves anyway**. A partially-initialised ERP that answers requests is worse than one that refuses to start. Fail closed, or at minimum refuse all non-health routes when `AMS_BOOTSTRAP_ERROR` is set.

### 4.4 Endpoint aliasing doubles the URL map

`_alias_unprefixed_endpoints()` registers every blueprint endpoint a second time without its prefix, producing 486 rules across two parallel blueprint trees (`app/blueprints/` and top-level `blueprints/`). Nothing broke in testing, but two names for one handler is a live shadowing risk whenever a name collides. Treat as tech debt with a deprecation path.

### 4.5 Operational notes

* **WeasyPrint native libraries are missing** in this environment, so any WeasyPrint-rendered PDF export will fail here. `reportlab` is installed and works. Confirm which library production actually uses before shipping PDF features.
* `tools/seed_demo_ledgers.py` is **broken** — its login is CSRF-blind and it dies at line 50 with `AttributeError: 'NoneType' has no attribute 'id'`. `tools/inventory/build_demo_db.py` (direct ORM) works.
* The repo's prior audit documents (`AUDIT_REPORT.md`, `QA_FULL_AUDIT.md`, `ORPHAN_SCENARIO_AUDIT.md`, `SCHEMA_FAILURE_REPORT.md`, `CONTINUATION_SUMMARY.md`) contain claims I could not reproduce and a "critical failure" framing contradicted by runtime evidence. They should be dated, superseded, or removed — stale audit docs cause real remediation effort to be misdirected.
* Unverified, flagged for follow-up: `instance/migration/purge_report.json` reports a purge dropping **11,687 of 36,272 rows**. I did not exercise the purge engine. Given §2.x, verify this was intentional before trusting it.

## 6. Recommendations, in order

1. **Add a positive-quantity guard to `add_record`** (`_dispatch_add_record.py:55`) — reject `qty <= 0` and treat unparseable input as an error. Closes §2.1.
2. **Add money invariants to `add_booking`/`edit_booking`** — `amount >= 0`, `0 <= paid_amount <= amount - discount`, on both create and edit. Closes §2.2.
3. **Sweep every other numeric form field for the same one-sided-comparison pattern.** §2.1 and §2.2 are the same bug in two places; assume there are more.
4. **Complete the plaintext-password migration** — run the repair script, verify zero rows, delete the fallback branch, drop the column.
5. **Add login rate limiting and lockout.**
6. **Point reports at `_minor` columns**, then extend the minor mirror to the sales models.
7. **Replace `frame-ancestors *` with an explicit host allowlist**; move the webhook token to an env var with no default and rotate it.
8. **Resolve the v4.4 schema situation** — commit the file (with `CHECK` constraints) or remove the pinning machinery. Add DB-level constraints as a backstop for items 1–3.
9. **Make bootstrap fail closed.**
10. **Add a CSRF test with `AMS_CSRF_ALWAYS=1`**, and regression tests for items 1 and 2.

### Note on item 8 — the v4.4 schema

`v44/SCHEMA_v4_4.sql` does not exist and, per `git log --all -- v44/`, **never
existed in this repository**. Authoring a replacement from scratch was
deliberately rejected: a hand-written DDL file would immediately drift from the
ORM models that actually build every database, reintroducing the same
false-authority problem in a worse form.

The pin was instead made *honest*:

- `app/services/v44_schema.py` gained `schema_bundle_available()` and
  `describe_schema_state()`, which report what is really on disk.
- Boot now records `AMS_SCHEMA_STATE` in config and logs an explicit warning
  that `AMS_SCHEMA_VERSION=v44` is configured while the bundle is missing, so
  the live schema is `orm-create-all` and **no SQL-level CHECK constraints from
  the bundle are in force**.
- The misleading per-restart log line (`Existing non-v4.4 database ... left
  untouched`, which implied a pending upgrade) was replaced with an accurate
  description of the steady state.

The DB-level `CHECK` backstop §6.8 asked for is therefore **not** in place; the
application-level guards from items 1-3 are the enforcement boundary. Committing
a real, generated-from-ORM schema bundle remains open as a follow-up and is a
governance decision rather than a bug fix.
